## TRACE-01：取水消耗真实成本，却连续产出 0

**状态：源头已修复。原始 trace 仍是旧程序的证据，没有重跑模型。**

农夫 `farmer_chen` 在 tick 7 创建取水出售计划。tick 8–21 期间，他发起并完成 7 次 `fetch_water`。每次配方声明产出 2 桶、消耗 1 单位水源和 5 点体力，实际完成事件却都是 0 桶水。tick 22 计划以 `produced=0` 被放弃。tick 31 又开始了一次取水，观测结束时尚未完成。

第一例的证据链：

1. `first seq 363 / tick 7`：选择 `start_plan(fetch_water)`。
2. `first seq 403 / tick 8`：选择 `craft(fetch_water)`。
3. `first seq 431 / tick 8`：事件 83 开工，`expected_yield=0`；当地水源从 5500 减到 5499，人物体力支付了开工成本。
4. `first seq 475 / tick 9`：事件 94，`crafted`，`quantity=0`；人物并未得到水，计划产量仍为 0。
5. 后续零产出完成：`first seq 564、668、770`；`resumed seq 105、207、296`。
6. `resumed seq 318 / tick 22`：选择放弃计划；最终计划保存为 `abandoned`，`produced=0`、`sold=0`。

源头是非生物生产的整数截断。水源下降到容量约 20% 后，声明的下限系数为 40%。`2 × 40 / 100` 的整数结果是 0。开工只拒绝系数为 0 的环境。资源和体力已经支付后，不足 1 桶的部分被丢掉。候选仍写“expect 2”。

修复后仍不凭空给 1 桶。已支付的分数按百分之一桶保存。40% 的 2 桶先记 80，第二次完成交付 1 桶并留下 60。连续五次交付 4 桶，余量为 0。七批一起做交付 5 桶，余量为 60。个人和匿名群体使用同一笔账。环境系数最高到 180 时，非生物配方仍不超过声明的 2 桶。系数为 0 时仍拒绝开工，不扣资源。恰好 1 单位水源和 5 点体力可以开工。未完成的批次先暂停时不交付物品，也不丢掉余量。

候选和开工记录使用同一次能交付的整数。这次若交付 0，就写 0，同时记下余量增加。审查仍把“产出 0 且没有增加余量”列为 `needs_review`。原始 trace 没有余量字段，所以那 7 次完成事件继续被标出。有余量增加的 0 产出不再当成丢掉的产量。

取水前水源从 27500 降到 5500，不是每刻都在导水。导水已经只在每天 07:00 走一跳。这次没有改导水频率，也没有改导水系数。

账目平衡和重放一致都不能证明旧的 0 产出是对的。原始 trace 保持不变。

## TRACE-02：进入完好房屋，工位仍被室外地点过滤

**状态：已复现源头错误，并在实跑之后修复；未重新调用模型验证行为改善。**

木匠 `carpenter_lu` 的目标是锯板。整个观测窗口没有一次 `craft`。他的初始房屋 `h_pingyuan_1` 有 `carpentry_bench`，状况为 90。场景没有供电系统。房屋声明区域，但没有单独声明场所身份。

`first seq 12 / tick 0`、`seq 236 / tick 5`、`seq 722 / tick 15` 的感知都把 `saw_planks` 列为不可开工。人物位于室外，必须先进入有权限的房屋，不能直接据此认定候选一定错误。

进一步做了独立对照：同一名人物、同样材料、同样完好房屋、同一工位预算，仅改变房屋是否声明场所。先执行合法进入，再实际制作。结果：声明场所的对照成功；仅声明区域的房屋失败，理由是没有空闲工位。

原因是 `productionFacility` 即使已收到明确的当前房屋身份，仍要求房屋的可选场所字段等于人物保留的室外场所。房屋工位因此被过滤了。修复后，人物已进入房屋时按该房屋找工位；室外查询仍按场所限制。独立对照现在都能支付材料、完成工时并实际产出。

测试：`TestLawProductionEnteredHouseProvidesItsOwnWorkstation`。它不是要求模型必须选锯板，而是证明合法进入后，实际存在且空闲的工位必须能使用。

## TRACE-03：系统把“当前没有可用设施”说成“设施损坏或没电”

**状态：已确认错误原因说明，并在实跑之后修正。**

上述三个木匠感知都给出 `production facility is damaged or lacks power`。但源函数在以下情况都会返回 false：当前地点没有设施、在别的房屋内、设施损坏或没有供电。这个布尔结果无法支持“损坏或缺电”的具体断言。

真实文本已经沿着这个说法展开。`first seq 278 / tick 5` 的木匠请求寻找“会修作坊家什的老手”，并说“锯又锯不成”。`resumed seq 825 / tick 31` 又说“家什修不好，板子锯不出来”。

源头说明现已改为“当前地点没有可用的所需生产设施”，不再凭空断言损坏。无法仅凭这次运行证明错误文字独自导致了全部停工；定位错误、模型规划能力和目标表示也可能参与其中。

木匠最终木板从 2 增到 4，不能用这个库存变化宣布“锯板目标已完成”。增加的 2 块来自船夫履约，见下文正面交付证据。

## TRACE-04：人物叙述了查仓、查堤，实际动作只有讲话

**状态：行为已确认，目标推进与叙述依据需要继续处理。**

`prov_inspector` 和 `magistrate_shen` 各选择了 32 次 `speak`。他们没有移动，没有实际维护或治理动作。库存和钱没有变化。文本则不断描述仓吏点粮、封仓、查看第三桩至第七桩、核对夫役与支粮等现场行为。

证据包括：

- 巡察者：`first seq 50、87`；`resumed seq 763 / tick 30`、`seq 819 / tick 31`。
- 知县：`first seq 52、89`；`resumed seq 765 / tick 30`、`seq 821 / tick 31`。
- `first seq 765 / tick 15` 的文本说“第四桩、第五桩的夯层，本官要亲自看过”，但最终动作仍只是对话；后续没有对应移动或检查。

引擎没有因为这些话就改仓库、堤坝或库存。声明与物理状态分离是有效的。但若产品期待人物真正办事，这些对话不能当成目标进展。

当前一般 `Goal` 是自然语言。持久计划只表示生产和出售，不能表示任意查仓、巡堤目标的完成条件。需要把可执行步骤、实际观察和完成条件接起来，才能验证目标是否推进。不能凭空设定“讲话超过 N 次就错”，也不能把所有不实发言都定为程序错误；人物本来允许说错或欺骗。
